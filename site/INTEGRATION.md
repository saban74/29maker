# 문의 폼을 회사 시스템에 연결하기 (입문자용)

지금 홈페이지의 문의 폼은 "받는 주소"가 비어 있어서 **아무 데도 보내지 않고** "온라인 접수 준비 중" 안내만 보여 줍니다.
받는 주소만 정해서 한 줄을 채우면 바로 연결되도록 만들어 두었습니다. 이 문서는 그 방법과, 회사 전산 담당자에게 무엇을 물어보고 전달해야 하는지 설명합니다.

문의는 **이메일**과 **그룹웨어** 두 곳으로 받을 계획입니다. 폼은 받는 주소를 여러 개 적을 수 있고, 하나라도 성공하면 방문자에게 "접수되었습니다"를 보여 줍니다.

---

## 1. 고칠 곳은 딱 한 곳

`site/contact.html` 에서 이 줄을 찾으세요.

```html
<form class="cform" id="contact-form" data-endpoints="">
```

따옴표 안에 받는 주소(웹 주소, `https://` 로 시작)를 넣습니다.

- 한 곳: `data-endpoints="https://받는주소.example.com/inquiry"`
- 여러 곳(쉼표로 구분): `data-endpoints="https://주소1.example.com/mail, https://주소2.example.com/groupware"`
- 비워 두기(지금 상태): 전송하지 않고 "온라인 접수 준비 중" 안내만 나옵니다. 버튼 글자는 "입력 내용 확인".
- 주소를 넣으면: 버튼 글자가 자동으로 "문의 보내기"로 바뀌고, 안내 문구도 "준비 중"에서 "작성 후 문의 보내기를 눌러 주세요"로 바뀝니다.

주소를 넣은 뒤에는 `contact.html` 의 노란 표시 `[확인 필요: 문의 접수 방법 연결 전]` 문구가 더 이상 보이지 않습니다(주소가 있으면 JS 가 안내 문구를 바꿉니다). 그래도 HTML 안의 처음 문구는 남아 있으니, 연결이 끝나면 `contact.html` 의 `form-notice` 문단과 `contact.html`/`contact-done.html` 의 "준비 중" 문장을 정리하세요.

## 2. 방문자에게 보이는 동작

| 상황 | 화면 |
|---|---|
| 보내는 중 | 버튼이 눌리지 않고 "보내는 중…" 표시 |
| 하나 이상 성공 | "접수되었습니다. 확인 후 연락드리겠습니다." 안내, 양식 비움, 버튼은 "문의 보내기"로 복귀 |
| 전부 실패(인터넷 끊김, 주소 오류, 15초 안에 응답 없음 등) | "전송에 실패했습니다. 전화·이메일로 문의해 주세요." + 대표전화 02-557-0505 |
| 스팸 프로그램이 숨은 칸을 채움 | 실제로는 보내지 않음 (사람 방문자에게는 보이지 않는 칸) |

개인정보 수집·이용 동의 체크는 계속 필수입니다. 체크하지 않으면 브라우저가 보내기 전에 막습니다.
안내 영역은 화면 읽기 프로그램이 읽어 주는 `aria-live` 영역입니다.

## 3. 받는 쪽으로 가는 내용 (JSON)

방문자가 "문의 보내기"를 누르면 각 주소로 **POST** 요청이 가고, 본문은 아래 모양의 JSON 입니다(`Content-Type: application/json`). 화면에 보이지 않는(선택한 문의 유형에 해당하지 않는) 칸은 빠집니다.

```json
{
  "type": "quote",
  "typeLabel": "견적 요청",
  "purpose": "열충격 시험",
  "industry": "자동차·모빌리티",
  "product": "TSA 시리즈",
  "count": "2",
  "temp": "-65 ~ +150°C",
  "humidity": "",
  "size": "",
  "standard": "AEC-Q100",
  "when": "2027년 상반기",
  "specFileName": "spec.pdf",
  "message": "견적 부탁드립니다.",
  "company": "OO전자",
  "name": "홍길동",
  "tel": "010-0000-0000",
  "email": "hong@example.com",
  "agree": true,
  "pageUrl": "https://(홈페이지 주소)/contact.html?type=quote",
  "submittedAt": "2026-11-04T05:30:00.000Z"
}
```

필드 이름 목록

| 이름 | 뜻 | 비고 |
|---|---|---|
| `type` | 문의 유형 코드 | `quote` 견적, `consult` 기술 상담, `material` 자료 요청, `as` A/S, `lab` 위탁 시험, `etc` 기타 |
| `typeLabel` | 문의 유형 한글 이름 | 사람이 읽기 쉽게 같이 보냄 |
| `purpose` | 시험 목적 | 견적·기술 상담만 |
| `industry` | 산업 분야 | 견적·기술 상담만 |
| `product` | 관심 제품·모델명 | 견적·상담·자료 요청·A/S |
| `count` | 필요 대수 | 견적·기술 상담만 |
| `temp`, `humidity` | 온도·습도 범위 | 견적·기술 상담만 |
| `size` | 필요한 용량·시험품 크기 | 견적·기술 상담만 |
| `standard` | 적용 규격 | 견적·기술 상담만 |
| `when` | 희망 도입 시기 | 견적·기술 상담만 |
| `specFileName` | 첨부한 시험 사양서의 **파일 이름만** | 파일 내용은 보내지 않습니다 (아래 주의 참고) |
| `labtest` | 위탁 시험 내용 | 위탁 시험만 |
| `message` | 기타 요청 | |
| `company`, `name`, `tel`, `email` | 회사명, 담당자, 연락처, 이메일 | 항상 |
| `agree` | 개인정보 수집·이용 동의 | 항상 `true` |
| `pageUrl` | 문의를 작성한 페이지 주소 | 어느 제품 페이지에서 왔는지 알 수 있음 |
| `submittedAt` | 보낸 시각 (UTC, ISO 형식) | 한국 시간은 +9시간 |

주의
- **파일 첨부는 이름만** 갑니다. 사양서 파일 자체를 받으려면 별도 개발이 필요하니, 지금은 "메일로 보내 주세요" 안내로 대신하는 것을 권장합니다.
- 받는 쪽은 **200번대 응답**(성공)을 돌려줘야 성공으로 처리됩니다. 300번대·400번대·500번대는 실패입니다.
- 필드가 나중에 늘거나 줄 수 있으니, 받는 쪽은 모르는 필드가 와도 오류를 내지 않게 만들어 달라고 요청하세요.

## 4. 연결 방식 세 가지 (장단점)

어느 방식이든 회사 전산 담당자의 확인이 필요합니다. 특정 서비스를 정해서 추천하지 않습니다.

### 방식 1. 그룹웨어 웹훅(또는 API)으로 바로 보내기
홈페이지가 그룹웨어가 알려 준 주소로 직접 보냅니다.
- 장점: 별도 서버가 필요 없습니다. 문의가 바로 그룹웨어(게시판, 메신저, 결재 등)에 쌓입니다.
- 단점: 그룹웨어가 외부 웹사이트에서 보낸 데이터를 받아 주는지 제품마다 다릅니다. 받는 주소가 홈페이지 방문자 눈에 보이는 코드에 들어가므로, 누군가 그 주소로 가짜 문의를 계속 보낼 수 있습니다. 보낼 수 있는 JSON 모양이 정해져 있으면 우리 데이터를 그 모양에 맞춰야 합니다.
- 확인할 것: 하이웍스, 네이버웍스, 다우오피스 등 **회사가 쓰는 그룹웨어가 웹훅 또는 API 를 지원하는지**, 지원한다면 어떤 주소로 어떤 모양의 데이터를 받는지.

### 방식 2. 이메일 전송 서비스로 보내기
폼 데이터를 받아 이메일로 바꿔 주는 외부 폼 전송 서비스, 또는 사내 메일 서버의 전송 API 로 보냅니다.
- 장점: 가장 간단하게 시작할 수 있고, 담당자는 평소 쓰는 메일로 문의를 받습니다.
- 단점: 외부 서비스를 쓰면 방문자의 개인정보가 **회사 밖(해외일 수도 있음)** 서버를 거칩니다. 서비스마다 월 전송 건수 제한과 비용이 다릅니다. 스팸 필터에 걸려 메일이 안 올 수 있습니다. 서비스가 받는 데이터 모양이 우리 JSON 과 다를 수 있습니다.
- 확인할 것: 사내 메일 서버가 외부에서 호출할 수 있는 전송 API 를 제공하는지, 또는 외부 폼 전송 서비스를 써도 되는지(개인정보 국외 이전 여부 포함).

### 방식 3. 권장안: 사내 서버(또는 작은 서버 함수) 하나가 받아서 메일과 그룹웨어에 동시에 전달
홈페이지는 **주소 하나**(`data-endpoints="https://..."`)로만 보내고, 그 주소를 처리하는 작은 프로그램이 이메일과 그룹웨어로 각각 전달합니다.
- 장점: 홈페이지 코드에는 주소 하나만 들어가 단순합니다. 접속 비밀번호·키를 서버 안에 숨길 수 있습니다. 스팸 걸러내기, 보관, 전달 실패 시 재시도를 서버에서 할 수 있습니다. 받는 곳이 바뀌어도 홈페이지는 고치지 않습니다. 개인정보를 회사가 통제하는 곳에 둘 수 있습니다.
- 단점: 서버(또는 서버 함수)를 만들고 관리해야 합니다. 개발 시간이 듭니다. 서버가 멈추면 문의가 안 들어오므로 모니터링이 필요합니다.
- 확인할 것: 회사에서 이런 작은 서버를 둘 수 있는지(사내 서버, 호스팅, 클라우드 등), 누가 운영하는지.

## 5. 회사 전산 담당자에게 전달할 내용

공통으로 전달
1. 홈페이지는 정적 파일(HTML/JS)이고, 문의 폼이 방문자 브라우저에서 **JSON POST** 를 보냅니다. (위 3장의 JSON 예시와 필드 목록을 그대로 전달)
2. 받는 주소는 `https://` 여야 합니다. (홈페이지가 https 인데 http 로 보내면 브라우저가 막습니다.)
3. 성공하면 **200번대 응답**을 돌려줘야 합니다.
4. 문의 하나당 한 번 호출됩니다. 주소를 여러 개 적으면 각 주소로 각각 한 번씩 갑니다.
5. 받는 사람(담당 부서, 이메일 주소 또는 그룹웨어 게시판·채널)이 누구인지.

방식별로 추가 전달·질문

- **그룹웨어 웹훅/API**: "저희 그룹웨어(제품명)에서 외부 웹사이트가 데이터를 보낼 수 있는 웹훅 또는 API 가 있나요? 있다면 ① 주소 ② 인증 방법(키, 토큰 등) ③ 받는 데이터 형식 ④ 보낼 수 있는 횟수 제한을 알려 주세요." 인증이 꼭 필요한 방식이면 홈페이지에서 직접 보내기 어려우니 방식 3 이 필요합니다.
- **이메일 전송 서비스/사내 메일 API**: "문의 JSON 을 받아 지정한 주소로 메일을 보내 주는 주소(엔드포인트)를 쓸 수 있나요? 보내는 메일 주소(발신자), 받는 메일 주소, 제목 형식, 하루 전송 한도를 알려 주세요." 외부 서비스라면 개인정보를 해외 서버에 보내도 되는지도 확인합니다.
- **사내 API / 작은 서버**: "위 JSON 을 받는 POST 주소를 만들어 주세요. 받으면 ① 담당자 메일로 전달 ② 그룹웨어로 전달을 하고, 둘 중 하나라도 성공하면 200 을 돌려주세요. 실패 내용은 기록으로 남겨 주세요. 같은 사람이 짧은 시간에 여러 번 보내는 스팸은 서버에서도 걸러 주세요."

## 6. 다른 도메인으로 보낼 때는 CORS 설정이 필요합니다

홈페이지 주소(예: `https://www.회사도메인.co.kr`)와 **받는 주소의 도메인이 다르면**, 브라우저가 보안 때문에 요청을 막을 수 있습니다. 이를 막지 않으려면 **받는 쪽 서버가 CORS 를 허용**해야 합니다. 전산 담당자에게 이렇게 요청하세요.

- 허용할 출처(Origin): 홈페이지 주소 (예: `https://www.회사도메인.co.kr`)
- 허용할 방식(Method): `POST` 와 `OPTIONS`
- 허용할 헤더(Header): `Content-Type`
- 브라우저는 JSON 을 보내기 전에 `OPTIONS` 로 먼저 확인하므로, `OPTIONS` 요청에도 정상 응답해야 합니다.

CORS 가 안 되어 있으면 서버에는 도착해도 화면에는 "전송에 실패했습니다"가 나올 수 있습니다. 시험 연결 때 이 점을 가장 먼저 확인하세요. 같은 도메인(홈페이지와 같은 사이트 주소 아래)으로 받으면 CORS 설정이 필요 없습니다.

또한 홈페이지 파일을 더블클릭으로 열었을 때(`file://`)는 브라우저가 외부 전송을 막는 경우가 많습니다. 연결 시험은 실제 웹 주소에 올린 뒤에 하세요.

## 7. 연결하기 전에 먼저 정해야 하는 것 (개인정보)

이 폼은 회사명, 이름, 연락처, 이메일을 받습니다. 개인정보이므로 **연결 전에** 회사에서 아래를 정해야 합니다.

1. **개인정보처리방침** 확정: 수집 항목, 이용 목적, 보관 기간, 제3자 제공·처리 위탁 여부를 `privacy.html` 에 채웁니다. (지금은 `[확인 필요]` 상태)
2. **보관 기간** 정하기: 문의 답변이 끝난 뒤 얼마나 보관하고 언제 지울지. 정해지면 `contact.html` 의 동의 문구 `보관 기간 [확인 필요]` 도 같이 고칩니다.
3. 외부 서비스(이메일 전송 서비스, 클라우드 등)를 쓴다면 **처리 위탁·국외 이전**에 해당하는지 확인하고 방침에 적습니다.
4. 문의 내용을 **누가 볼 수 있는지**(접근 권한)와 받은 메일·그룹웨어 글을 **언제 어떻게 삭제하는지** 정합니다.
5. 사양서 첨부 파일을 받는다면 그 파일의 보관·삭제도 같은 기준으로 정합니다.

법적 판단이 필요한 부분은 회사 내부 담당자 또는 전문가에게 확인하세요. 이 문서는 법률 자문이 아닙니다.

## 8. 연결 후 시험 순서

1. `data-endpoints` 에 시험용 주소를 넣고 실제 웹 주소에 올립니다.
2. 문의 유형을 하나씩 바꿔 가며 보내 보고, 이메일과 그룹웨어에 모두 도착하는지 확인합니다.
3. 받는 주소를 일부러 틀리게 해서 "전송에 실패했습니다" 안내가 나오는지 확인합니다.
4. 휴대폰에서도 한 번 보내 봅니다.
5. 시험 데이터를 지우고, 진짜 주소로 바꾼 뒤 `contact.html` 의 "준비 중" 문구를 정리합니다.
